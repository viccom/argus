# 文档管理规范

> 状态：生效
> 生效日期：2026-10-21
> 适用范围：argus 仓库 `docs/**`
> 说明：本规范只约束“新文档怎么写、放哪、如何登记”，不要求搬迁存量文档。冲突时以更具体、更新者为准，并回改另一方。

## 1. 权威源分层（单一事实源）

| 内容 | 唯一权威源 |
|---|---|
| 端点、环境变量、模型来源 | `README.md` |
| 仓库入口、构建、硬纪律 | `AGENTS.md` |
| 能力进度 | `docs/engine-exposure-plan.md`、`docs/yolo-rs-absorption-plan.md`、`docs/homepix-integration-plan.md` |
| 踩坑与模型判别法 | `docs/e2e-and-models.md` |
| 设计决策 | `docs/designs/` |
| 文档规范 | `docs/conventions/` |

规则：同一事实只在一处维护，其他文档用链接引用，不复制正文。发现漂移先回改权威源，再同步引用方。

## 2. 目录与命名

- `docs/conventions/<topic>.md`：规范类文档。
- `docs/designs/YYYY-MM-DD-<topic>-design.md`：设计文档。
- `docs/plans/YYYY-MM-DD-<topic>-plan.md`：实施计划（由 writing-plans 产出）。
- 存量 `docs/*.md`（三张计划表、调研、踩坑）保持原名与位置，不搬迁、不改名。
- 文件名一律小写连字符；日期用 ISO `YYYY-MM-DD`；主题用英文短横线短语。

## 3. 文档头（新文档必填）

每份新文档开头写状态块：

```
> 状态：draft | approved | implemented | superseded
> 日期：YYYY-MM-DD（创建或最近一次实质修改）
> 基线：适用代码 commit（设计/计划文档必填）
> 权威源：相关计划表 / README 链接
> 取代关系：superseded 时指向替代文档
```

## 4. 设计文档必备章节

1. 背景与目标 / 非目标
2. 代码现状（证据：`path:line` + 基线 commit）
3. 决策与备选（为什么不是其他方案）
4. 架构与数据流
5. 契约与兼容性（明确加法/破坏性）
6. 错误处理与安全边界
7. 风险登记（级别 / 缓解 / 验证手段）
8. 测试策略
9. 实施阶段与门禁（详细任务拆解放 `docs/plans/`）
10. 验收标准（可执行、可判定）
11. 回滚
12. 未决项 / 后续
13. 变更记录

## 5. 进度与状态

- 进度只回填三张计划表，格式：状态 + 验证证据 + 日期；设计文档不承载进度。
- 设计批准后状态改 `approved`；实现完成改 `implemented` 并在计划表销账；被替代改 `superseded` 并指向替代文档。
- 实测数字必须带时点（如“2026-10-21 实测”）；禁止写会腐烂的裸计数。
- 验证证据只接受命令 + 真实输出，或可复现的实测记录；不写“应该可以/理论上”。

## 6. 索引

- 新增、改名、废弃文档必须同步 `docs/README.md` 索引：一行 = 链接 + 一句话用途 + 状态。
- 索引不复制正文，只做导航。

## 7. 写作纪律

- 中文；术语与代码保持一致（能力键、端点名、env 名以 README/代码为准）。
- 引用代码用 `path:line` 并注明基线 commit；跨仓库引用写清仓库与版本。
- 不把凭据、真实内网地址、token 写进文档；示例用占位符。
- 设计文档与实施计划分离：设计讲“为什么/是什么”，计划讲“按什么顺序做、怎么验收”。
