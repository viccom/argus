## 0. 五分钟读懂：先记三句话

如果你只想尽快把服务跑起来，记住这三条，细节以后再看：

1. **一张图变快的钥匙 = GPU**；**一堆图变快的钥匙 = 开池（多开窗口）+ 让门外不堵**。CPU 上「多开窗口」不会让单张图变快，甚至不会让总吞吐变快。
2. **调并发只调两个数**：`ARGUS_ENGINE_POOL`（开几个窗口）和 `ARGUS_MAX_CONCURRENT_INFERENCE`（大厅一次放几个人）。硬性关系：**大厅放行数 ≥ 各能力的窗口数之和**，否则窗口白开。
3. **CPU 与 GPU 是两套逻辑**：CPU 共享机保持默认（池 1）最稳；GPU 机器必须把池开到 4–8、显存上限设好、预热做完，否则等于买跑车挂一档。

**阅读路线**：
- 只想配置一台机器 → 直接看 §8「从零配置一台机器」的填空步骤，回头再查 §6 场景表；
- 想知道「为什么这么配」 → 读 §2（三道门）→ §4（CPU/GPU 本质区别）→ §5（选型）；
- 遇到性能问题 → 读 §7（误区 FAQ）+ §9（诊断观测）。

## 2. 并发模型：一张图要过三道门

### 2.1 银行柜台类比（先看懂这张图）

把 argus 想成一家银行营业厅，图片就是来办业务的客户：

- **窗口（实例）**：一个柜员，一次只办一个客户（办 = 一次模型前向）。
- **窗口内栏杆（实例内串行）**：同一窗口前的客户必须排队，一次放一个进去。
- **池**：同一业务开 N 个窗口，客户轮流（round-robin）分到窗口，N 个窗口能同时办 N 个客户。
- **全局闸**：大厅安检门，整栋楼一次只放 X 人进去办业务，其余在大厅坐着等叫号。

**调参的本质只有两件事：开几个窗口（池）、大厅放行多少人（全局闸）。** 窗口内那道栏杆是固定建筑，为什么拆不动、也不用拆，见 §2.4。

### 2.2 一张图的完整旅程（按时间先后）

```
到达
 → 门外① 鉴权：核对 API key（几乎不耗时）
 → 门外② 拆包（不占闸门名额）：解析 multipart、JPEG 解码、参数校验、像素数闸门
        ↑ 这些活在 CPU 上、spawn_blocking 里做，先于任何引擎触发（AGENTS.md 硬纪律 4）
 → 门③ 大厅安检门（全局闸）：有放行名额就进；没有就等（等待时长 = 响应里的 queue_ms）
 → 门② 叫号机（池闸）：轮流分到一个窗口——注意是"轮流"不是"挑空闲窗口"
 → 门① 窗口内栏杆：该窗口的柜员空吗？空→立即办；忙→栏杆前等
        ↑ 这段等待被算进 inference_ms，不算 queue_ms
 → 办业务：一次模型前向（CPU 用 4 线程；GPU 用 CUDA 流）
 → 门外③ 后处理：NMS 去重、组 JSON、返回；腾出全部三道门的位置
```

编号说明：**门①/②/③** 是本文对三道闸门的固定编号（下文所有 § 引用都用它）；「门外①/②/③」只是这趟旅程里的步骤顺序，不参与闸门编号。三道门按请求遇到的先后是 **③ → ② → ①**（先过大厅、再叫号、最后窗口栏杆）。

代码锚点（基线 `0cee46c`）：门③ `routes/common.rs:151`；门② `engine.rs:1045`；门① fork `base.rs:101`。

**术语 ↔ 代码 ↔ 参数对照**（把类比落到实物上）：

| 类比 | 代码实物 | 对应 env |
|---|---|---|
| 大厅安检门 | `inference_semaphore` | `ARGUS_MAX_CONCURRENT_INFERENCE` |
| 窗口数量 | `EnginePool.instances` 的长度 | `ARGUS_ENGINE_POOL` / `ARGUS_<CAP>_POOL` |
| 窗口内栏杆 | `Mutex<Session>` | 无（fork 写死） |
| 等不及就拒绝 | `acquire_permit` 超时/try_acquire | `ARGUS_ACQUIRE_TIMEOUT_MS` |

### 2.3 三道门对照表

| 门 | 由什么控制 | 代码默认 | 本机生产实际 | 能否配置 |
|---|---|---|---|---|
| ① 窗口内栏杆 | fork 把 ORT Session 包在 `Mutex` 里 | —（一次 1 张） | 同左 | **不可配**（§2.4） |
| ② 窗口数 | `EnginePool` 实例数 = 池 permit 数 | **1** | 1（warden env 未设置 POOL） | `ARGUS_ENGINE_POOL`（全局）/ `ARGUS_<CAP>_POOL`（单能力） |
| ③ 大厅放行数 | `inference_semaphore` | **0 = 不限**【代码】 | **2**（`~/.config/warden/argus.env` 注入） | `ARGUS_MAX_CONCURRENT_INFERENCE` |

> 表里特意区分「代码默认」与「本机生产实际」：读者查 `/health` 看到 `max_concurrent=2` 时，那是 warden 注入的部署值，不是 argus 自带默认。

### 2.4 窗口内串行是"写死"的吗？——是代码设计，不是配置开关

**是硬编码在 fork 里的**【代码】：rust-onnx-infer fork 的引擎基座 `src/core/base.rs:101` 声明 `session: Mutex<Session>`，前向入口 `run_multi_output`（base.rs:421）在锁内完成整个前向 + 输出快照拷贝。同一窗口上的并发请求在此排队，一次只放一个前向；argus 侧没有任何 env 能改变它（`engine.rs:146` 注释写明这个前提）。

**为什么这样设计**（两个原因都站得住）：
1. **CPU 上不亏**：一次前向内部已用 4 个线程并行（§3），窗口内串行不浪费核；放开并发只是让多张图分同一批核，总吞吐不变（核数守恒，§4.1）。
2. **实现简单安全**：ORT 输出值挂在 session 内部缓冲上，锁内快照拷贝避免并发读写的生命周期问题。

**能不能拆？** 技术上能——ORT 的 `Session::run` 支持 `&self` 并发调用，改 fork 去掉 Mutex 即可；ORT 官方文档也提到多个 session 可以共享全局线程池以避免争抢（【官方】[Thread management](https://onnxruntime.ai/docs/performance/tune-performance/threading.html)）。但**不值得**：CPU 上无吞吐收益；GPU 上同一 session 的并发前向仍挤同一条 CUDA 流；池（多开窗口）已经用"复制实例"绕开了这道栏杆。**结论：不要动①，要并行去开②。**

### 2.5 池是什么：同一模型加载 N 份独立副本

`ARGUS_ENGINE_POOL=N` 不是"复用"，而是启动时把同一个模型**完整加载 N 次**【代码】：N 份权重、N 个独立 ORT Session、互不干扰。请求轮流分到某个窗口，N 个窗口就能真正同时推 N 张图。

代价（预算公式来自 README 与 `engine.rs` 的 `EnginePool` 注释）：
- **内存** = 模型大小 × N × 已加载引擎数（GPU 上另算显存，见 §4.2）；
- **CPU 核数** ≈ N × 4（每窗口 4 线程，§3）；共享机别超；
- N=1 时与改造前单实例行为完全一致——这就是零回归默认。

**排队还是拒绝**：`ARGUS_ACQUIRE_TIMEOUT_MS`（默认 30000）决定——大厅满了就等，等超时返回 503；设 0 = 立即拒绝（fail-fast）。生产 GPU 建议 0 配合「大厅数 = 窗口数」防雪崩；内网低负载留默认排队更友好。

**两个指标别读错**：
- `queue_ms` 大 → 大厅太小或窗口不够（③/②）；
- `inference_ms` 比独跑值大数倍 → 图在窗口栏杆前撞 Mutex（②太小）。

**联动硬约束：`大厅放行数 ≥ Σ(各能力窗口数)`**。反过来（池 4、闸 2）窗口永远跑不满。【实测】2026-11-10 本机 4 并发 /detect（闸 2、池 1）：`queued_total=2`，两个获准请求在同一窗口互等 Mutex，单请求 inference_ms 从独跑 63ms 拉长到 120–145ms，**总吞吐不变**。

`ARGUS_SHUTDOWN_TIMEOUT_SECS` 要覆盖「最长推理 × 排队深度」，开池后排队可能翻倍，需重新核算（SAHI/depth 单次 ~1.5s）。

### 2.6 实战走位：300 张图过三道门

② 的叫号是**轮流派号，不是挑空闲窗口**：池=2 时请求交替派往 A/B 窗口，派到忙窗口就在①栏杆前等，这段计时落在 `inference_ms` 而不是 `queue_ms`。图像解码在所有门之前，不占闸门名额。

客户端怎么发，决定三道门是否真的排队：

| 客户端打法 | 本机现状（闸 2 / 池 1）的走位 |
|---|---|
| **串行发**（发一张收一张） | 三道门全程空转，总耗时 ≈ 300 × ~0.1s ≈ 30s，每张 queue_ms=0。**共享机现状下的正确打法** |
| **齐发 300 张** | 瓶颈=窗口（池 1）→ 吞吐约 12 张/s，总耗时 ~25s；队尾 queue_ms ~24s，**逼近默认 30s 排队超时线**，再加量开始吃 503 |
| 齐发 + fail-fast（超时=0） | 除前 `max_concurrent` 张外全部立即 503——大批量严禁此组合 |

同一批 300 张，把门放大后走位完全不同（yolo 系 detect@640，【实测】2026-11-10 本机独跑 83ms 折算；GPU 行为【估算】需上机压测）：

| 配置 | 瓶颈 | 吞吐 | 300 张总耗时 | 队尾 queue_ms |
|---|---|---|---|---|
| 本机共享机（闸 2 / 池 1） | ①窗口 | ~12/s | ~25s | ~24s（贴 503 红线） |
| CPU 独占 16C（闸 10 / 池 4） | 核数 | ~48/s | ~6.5s | ~6s |
| GPU 单卡 A10（闸 16 / 池 8） | GPU | ~200/s【估算】 | ~1.5s | ~1.5s |

批量客户端建议：并发数 ≈ `max_concurrent`（本机 2、独占机 10、GPU 16），队列最短、不触发超时；本机现状直接串行发最稳。

## 3. ORT 线程数：官方吃满核，本 fork 钉死 4

这一节解释「为什么窗口吃 4 个核」，是后面所有预算公式的源头。

- **ORT 官方默认**【官方】：`intra_op_num_threads=0`（未设置）时，线程总数 = **物理 CPU 核数**，并且把线程绑定（affinity）到各核上；`inter_op` 线程池只在 `ORT_PARALLEL` 模式下才创建。见 [Thread management](https://onnxruntime.ai/docs/performance/tune-performance/threading.html)。也就是说，原生 ORT 在一台 16 核机器上单窗口就想吃满 16 核。
- **本 fork 的定制**【代码】：`src/core/runtime_config.rs` 把 `DEFAULT_INTRA_OP_THREADS` 和 `DEFAULT_INTER_OP_THREADS` 都**硬编码为 4**，与设备无关；argus 侧没有 env 暴露。代码注释写明动机是"与原版历史行为一致"，实际效果则是**共享机自律**：本机 16C 上还住着 safebot-go、双 vl-gateway、GitLab runner 等，单个 argus 窗口只占 4 核，把其余核让给邻居。
- **含义随设备不同**：
  - **CPU**：这 4 线程是单图并行的主角——一张图已经用满 4 核；「窗口数 × 4 ≈ 可用核数」的预算公式由此而来。
  - **GPU**：前向主体在 CUDA 流上，这 4 线程只管 CPU 侧参与部分，窗口数不受「×4 ≈ 核数」约束。
- **想改怎么办**（挂账 §10.1）：改 fork 的常量并 env 化。注意 ORT 官方明说手动设定线程数后**不再自动绑核**，多窗口并行时反而可能互相抢核（官方建议这种场景用全局线程池或显式 affinity）——所以"调大线程数"不是免费午餐。

### 3.1 "4"的出处与实测复核（2026-11-10）

**出处考证**：fork 的 `runtime_config.rs` 文件头只写了"默认值与原版历史行为一致"，`session_factory.rs` 同样写"默认行为与原版一致"；追到上游初始提交 `57249e7`（2026-09-06，作者 xgc）第一版就是 4，之后从未改动、也无 commit 讨论过它。**仓库里没有留下"为什么是 4"的选型依据**——结合代码里大量 Java/C++ 风格命名（`runInference`、`OnnxSessionFactory`），更像是上游项目的历史折衷值（早年 4–8 核开发机的常见默认），不是针对本模型/本机的基准测试结果。特别注意：`DEFAULT_INTER_OP_THREADS=4` 在官方默认的 `ORT_SEQUENTIAL` 模式下几乎不起作用（§3 官方资料），一个不生效的参数也被认真设成 4，是"移植遗留"的佐证。

**"4 个线程 = 4 个核"的准确说法**：是**最多约 4 核的算力额度**，不是独占 4 个物理核——手动设定 intra 线程数后 ORT 不再自动绑核，线程由 OS 在 16 核上自由调度；且模型有串行段、内存等待，实际利用率通常达不到 400%。

**实测复核（线程数 sweep）**：在共享 venv 中装**与生产同版本**的 ORT **1.26.0**（隔离目录 `/tmp/ort126probe/pkgs`，不动共享 venv），同一模型 yolov8n.onnx、640×640 零张量，`inter_op=4` 与 fork 一致，每档预热 3 次、测 15 次取中位数；正反两种顺序各跑一遍排除机器负载漂移：

| intra | 单张纯 `session.run` 延迟（正序/反序） | 相对 1 线程 |
|---|---|---|
| 1 | 100.3 / 97.7 ms | 1.00× |
| 2 | 59.3 / 60.5 ms | ~1.65× |
| **4（fork 默认）** | **37.5 / 37.7 ms** | **~2.65×** |
| 8 | 35.2 / 28.9 ms | ~2.9×（平台期起点） |
| 12 | 37.2 / 30.9 ms | 平台期 |
| 16 | 34.9 / 29.7 ms | ~2.9×，抖动明显变大（max 66.9ms） |

结论：**4→8 只有约 10–20% 收益，8 线程后进入平台期，16 线程绝不带来 4 倍线性加速**；线程越多延迟抖动越大。另一版 ORT 1.29.0 的 sweep 趋势一致（4→8 到顶、16 略倒退），说明这是模型/硬件特性而非版本偶然。

**固定总预算 16 线程，怎么花更划算**（每窗口独立 Session 模拟 argus 池化，50 张/窗口并发，ORT 1.26.0）：

| 分配方式 | 总 QPS | 单张 p50 延迟 |
|---|---|---|
| intra=1 × 16 窗口 | **79.8** | 167 ms |
| intra=2 × 8 窗口 | 68.3 | 103 ms |
| **intra=4 × 4 窗口（§6 场景 B 推荐档）** | **58.5** | **64 ms** |
| intra=8 × 2 窗口 | 35.9 | 47 ms |
| intra=16 × 1 窗口 | 25.7 | 37 ms |

规律：**"少线程多窗口"总吞吐高、"多线程少窗口"单张延迟低**，二者在固定核预算下是对赌关系。这也解释了 §6 场景 B 为什么推荐"池开到 4"而不是把 intra 从 4 调成 16——**核预算没用满时，优先拿去多开窗口**。

> **实验边界（读结论时务必带上）**：以上测的是纯 `session.run`（模型前向），**不含 argus 侧的解码/letterbox/NMS 与 HTTP 开销**；这些固定串行段在生产 `inference_ms` 里占一部分（生产独跑 ~83ms vs 实验纯前向 ~38ms），所以"调线程数"在真实服务里的收益比表中更小。数值用于看**趋势与相对关系**，不能直接当生产 SLA。跨机器/跨模型/跨输入尺寸需各自重测。

## 4. CPU 与 GPU 的本质区别（全文最核心的一节）

### 4.1 吞吐模型：为什么 CPU 开池不涨、GPU 开池才涨

**CPU：核数守恒，池化不涨总吞吐。**
一张图内部已经用满 4 线程；核数固定时，总吞吐 ≈ 有效核数 ÷ 每图核·秒，**与窗口数无关**。开更多窗口只是把同一批核分给多张图（每张变慢、总速率持平），还多出内存带宽争抢。【实测】2026-11-10 本机 16C：并发 2 时单请求 63→120/145ms，聚合吞吐不变。ORT 官方也指出多 session 各自起线程池会造成超订阅（oversubscription）与争抢【官方，同上文档】。**所以 CPU 共享机上"池 1"是正确默认**：单张延迟最低、内存最小、不挤占同机服务。

**GPU：池化是第一吞吐杠杆。**
单个窗口的前向在一条 CUDA 流上排队执行；而解码、letterbox、NMS 都在 CPU 上做，这些期间 GPU 闲着。开多个窗口时，B 窗口的前向能填进 A 窗口的 CPU 空隙，GPU 利用率实涨（流水线重叠）。yolo-rs 时代 A100 ~500 QPS（【实测锚点】仓库 Dockerfile 记录，cuDNN 9.8）就是"多窗口池化、非批处理"形态跑出来的。

| | CPU | GPU |
|---|---|---|
| 池化的作用 | 重排延迟分配，总吞吐不变 | 填满流水线空隙，吞吐实涨（×3–5 量级【估算】） |
| 窗口数上限约束 | 窗口数 × 4 ≈ 核数 | 显存（每窗口 ~3GB）与利用率 |
| 推荐池 | 1（共享机）/ 4（独占机） | 4–8 |

一句话：**同一套代码，CPU 串行是对的，GPU 串行是浪费。**

### 4.2 内存：两本账分开算

- **CPU → 系统内存（RAM）**【实测】：Σ(模型大小 × 窗口数 × 已加载引擎数) + 每窗口工作区。2026-11-10 本机实测：池 1、6 个引擎（detect/ppe/fire_smoke/cls/obb/seg）合计 RSS **0.69GB**；README 记录的全能力池 4 = **12.4GB**（其中 OCR/HUMAN_PARSING/DEPTH 三项占 ~10.3GB）——大模型能力是内存治理杠杆，可单独压它的池。
- **GPU → 显存（VRAM）**：ORT 的 CUDA EP 用 **arena 显存池**【官方】：`gpu_mem_limit` 默认 SIZE_MAX（不限），`arena_extend_strategy` 默认 `kNextPowerOfTwo`（按 2 的幂扩张），且官方明确"arena 上限只约束 EP 的显存池，总显存占用可能更高"（[CUDA EP](https://onnxruntime.ai/docs/execution-providers/CUDA-ExecutionProvider.html)）。本 fork 注释记录的实测：A100 单 yolov8n 窗口 ~2.9GB，池 4 饱和 11.4GB；不设上限曾与 vLLM 共存膨胀至 81GB 打死服务（cuBLAS OOM 后永久失败）。

> 用户常见疑问："我本地 A100 测的时候显存才几个 G 啊？"——对，那是**单窗口**的 ~3GB 峰值；窗口数 × 每窗口峰值才是总量，且 arena 只增不减，所以**生产 GPU 必设 `ARGUS_GPU_MEM_LIMIT_MB`**，并留「官方所说 arena 之外」的余量。fork 里这个上限是**进程级**的（所有窗口共用一个上限），不是每窗口各设一份【代码：`runtime_config.rs` 的 `GLOBAL_GPU_MEM_LIMIT_MB`】。

### 4.3 预热：为什么 GPU 上必须做

- **CPU**【实测/README】：预热只消除首请求的懒加载抖动，稳态吞吐无收益（关预热首推理 6.5s ≈ 热态）。
- **GPU**【官方 + 实测】：ORT CUDA EP 的 `cudnn_conv_algo_search` 默认 **EXHAUSTIVE**（穷举卷积算法，为每个 Conv 节点挑最快实现并分配 workspace），且官方 CUDA Graphs 文档明说"第一次 `Run()` 要做显存分配、图捕获等，延迟必然高"；此外首次 CUDA 上下文初始化也在此列。不预热 → 首批并发请求集体卡顿。argus 的 `EnginePool::warmup` 对每个窗口各跑一次假图前向，正是把这些一次性开销提前烧掉（`ARGUS_<CAP>_WARMUP_SIZE` 沿用）。

### 4.4 单图资源账单（容量换算的分子）

窗口办一张图要消耗多少资源？【实测】2026-11-10，x86 16C 共享机，独跑 inference_ms：

| 能力 | 办理时长 | CPU 消耗 | 相对 detect |
|---|---|---|---|
| classify | 5ms | 0.02 核·秒 | 0.06× |
| obb | 65ms | 0.26 核·秒 | 0.8× |
| **detect** | **83ms** | **0.33 核·秒**（83ms × 4 线程） | **1×** |
| pose | 84ms | 0.34 核·秒 | 1× |
| segmentation | ~400ms | ~1.6 核·秒 | **~5×** |

配套项（detect@640）：
- **窗口常驻内存**：每窗口 ~100–400MB【实测折算：0.69GB ÷ 6 引擎】，开张即占、长期持有；
- **单次瞬时内存**：输入张量 640×640×3×4B ≈ 4.9MB + 缩放/NMS 中间缓冲，几十 MB，办完即释放；
- **门外解码**：~0.008–0.1 核·秒【估算，随图大小】，不占闸门名额；
- **GPU 窗口**：显存开张费 ~2.9GB/窗口【实测锚点，A100】；单张 GPU 算力 A100 推算 ~2ms【估算：由 500 QPS 锚点反推】；解码/缩放仍在 CPU（所以每张卡要配 ≥8 vCPU）。

**账单 → 容量**：单窗口吞吐 = 1 ÷ 办理时长（detect ≈ 12 张/s，持续烧 4 核）；整机吞吐 = 有效核数 ÷ 单张核·秒（16C ÷ 0.33 ≈ 48 张/s，正是 §2.6 独占机那行）。混合负载按权重折算：1 张 seg ≈ 5 张 detect。

### 4.5 单窗口能靠"多分资源"变快吗？

**CPU：不能直接快——窗口速度被"固定 4 线程"锁死**（§3）。给它 8 核也只开 4 线程。三种正确姿势：

| 姿势 | 做法与效果 | 代价/边界 |
|---|---|---|
| **加核 → 多开窗口** | 总吞吐变快（§4.1 核数守恒），单张延迟不变 | 无，但有核上限 |
| **护核 → 防争抢** | 共享机上邻居抢核会拉长 83ms 的实际执行；独占部署 / systemd `CPUAffinity` / cgroup 权重把实测值兑现；ORT 官方也建议多 session 时把线程池绑到不同核避免争抢【官方】 | 部署动作，零代码 |
| **加线程 4→8** | 需改 fork（§10.1）。【实测】ORT 1.26.0 sweep（§3.1）：4→8 单张纯前向仅快约 10–20%（37.5→35.2ms），8 线程后进入平台期、16 线程抖动显著变大；受 Amdahl 定律与内存带宽限制，非线性的 4 倍 | 单窗口吃 8 核 → 同核可开窗口减半；**单张延迟与总吞吐对赌**（§3.1 并发实验：固定 16 线程预算时 intra=4×4 窗口 QPS 58.5，intra=16×1 窗口仅 25.7），共享机违反资源纪律 |

**GPU：显存 ≠ 速度。** 显存只决定能开几个窗口，单张速度换卡/换管线才变快。杠杆排序：换更强的卡（×2–4【估算】）> TensorRT EP（×2–5【估算，§10.4 未实测】）> FP16 > 输入降档 640→320（×2.4–4【估算】，精度换速度）。注意 GPU 窗口的瓶颈常在**门外 CPU 段**——卡越快，解码/缩放占比越大，"给 GPU 窗口提速"常等于给实例配更多 vCPU。

**量化示例：detect 83ms 压到 40ms 的三条路**
1. 输入 640→320：≈35ms【估算】✓ 零代码，但要用真实图验证小目标检出率
2. 护核（当前处争抢态时）：回到 83ms 基准 ✓
3. intra 8 线程：纯前向只省 ~2ms、且生产里还被固定串行段稀释（§3.1），单独用达不到目标 ✗

想快一个数量级只有换赛道：GPU 窗口（单张 GPU 段 2–6ms【估算】）。

## 5. 选型指南：买什么样的机器

### 5.1 先回答三个问题，再算数

1. **每秒多少张图？** 图片 API 的持续 QPS、峰值 QPS 各是多少（"600 张/秒"是持续还是突发，结论差好几倍）？
2. **视频怎么接入？** argus 只收 HTTP 图片，**不直接吃 RTSP 视频流**；16 路视频需要先有解码服务抽帧成图片再发给 argus。按"路数 × 每路每秒抽几帧"折算成 QPS（16 路 × 25fps 全帧率 = 400/s；抽 5fps = 80/s）。
3. **跑哪些能力？** 只有 yolo 系 detect/cls/obb/pose/seg 时按 §4.4 账单折；有 seg 按 5 倍权重折。

### 5.2 决策树与两个公式

```
目标吞吐（折算成 detect@640 等效 QPS）
├─ ≤ ~20 QPS 且负载是零星的 → 现有 CPU 共享机即可，别折腾
├─ 20–50 QPS → CPU 独占机（16C/32GB 一档）
├─ 50–150 QPS → 大 CPU 独占机（32C+）或 1 张入门 GPU，按预算与运维习惯
└─ 数百 QPS / 多能力混合 / 实时视频 → GPU（单卡先测，不够再加卡/加实例）
```

- **CPU 核数** ≈ 目标 QPS × 单图核·秒（detect@640 ≈ 0.33）× 余量 1.5。例：24 QPS → 24×0.33×1.5 ≈ 12 核 → 选 16 vCPU / 32GB 计算型。
- **GPU 卡数** ≈ 目标 QPS ÷ 单卡吞吐（§5.4 表）；显存预算 = Σ(窗口数 × ~3GB) + 余量。

### 5.3 CPU 机型怎么挑

- 计算优化型（c 系）、内存按 §4.2 账单算并留 2 倍余量；
- 参照点【实测 2026-11-10】：本机 16C/31G 是**共享机**，argus 峰值只占 2–4 核、~1.5GB；独占机上整机核数才归 argus 用；
- 内存吃紧时优先压 OCR / 人像解析 / 深度三能力的池（README 实测这三项占全能力池 4 的 ~10.3GB）。

### 5.4 GPU 机型怎么挑

**四个硬条件（缺一不可）**：
1. **NVIDIA 卡**：ORT CUDA EP 面向 NVIDIA；昇腾等国产卡需要 CANN 定制版 ORT，当前 argus 不支持；
2. **x86 主机**：ORT 官方 aarch64 包只有 CPU 版（【实测】2026-11-09 交叉编译验证），ARM + CUDA 需自行源码编 ORT；
3. **驱动/CUDA/cuDNN 版本与 ORT 包匹配**【官方】：ORT **1.26.x（本 fork 钉死）↔ CUDA 12.8 + cuDNN 9.x**；ORT 1.27+ 默认改用 CUDA 13.0，混用会加载失败。仓库 `deploy/docker/Dockerfile` 已钉死 `nvidia/cuda:12.8.1-cudnn-runtime-ubuntu22.04`，直接用这条基线最省心；
4. **每张卡配 ≥8 vCPU**：数百 QPS 的解码 + 缩放要 9–12 核【估算】，GPU 再快也替不了门外的 CPU 活。

**单卡吞吐参考**（yolov8n@640，多窗口池化、非批处理）：

| 卡 | 显存 | 吞吐 | 依据 |
|---|---|---|---|
| A100 80G | 80GB | ~500/s | 【实测锚点】yolo-rs 时代，cuDNN 9.8（同负载 cuDNN 9.1 仅 ~256/s） |
| A10 24G | 24GB | ~150–250/s | 【估算】约 A100 的 1/3 算力，**上机压测为准** |
| T4 16G | 16GB | ~80–120/s | 【估算】 |

**降本杠杆**：输入 640→320/416 单卡吞吐 ×2.4–4【估算，需真实图验证精度】；服务端批处理 ×2–4【估算，代码挂账 §10.2】；竞价/按量实例先测后买。

### 5.5 多卡注意：一个 argus 实例只用一张卡

fork 的 `DEFAULT_GPU_DEVICE_ID = 0` 固定【代码】，且官方 CUDA EP 的 `device_id` 默认也是 0【官方】——**一个实例只绑一张卡**。N 卡需求 → 起 N 个 argus 实例（不同端口/容器），上层由 safebot-go 检测池的多实例 failover 调度；"单实例管多卡"要改 fork（挂账 §10.3）。

## 6. 推荐配置组合（联动后的场景表）

参数全集与默认值见 README；以下只给**联动组合**。设完必须过一遍 §8.3 核对清单。

**A. CPU 共享机（本机现状：argus 与其它服务同居）**

```bash
ARGUS_DEVICE=cpu
ARGUS_ENGINE_POOL=1                 # 核让给同机服务；CPU 开池无吞吐收益
ARGUS_MAX_CONCURRENT_INFERENCE=2    # 大厅放行数（本机 warden 注入值）
# ARGUS_ACQUIRE_TIMEOUT_MS 留默认 30000：内网低负载排队式友好
```

**B. CPU 独占机（argus 独享 16 核）**

```bash
ARGUS_DEVICE=cpu
ARGUS_ENGINE_POOL=4                 # 4 窗口 × 4 线程 ≈ 16 核
ARGUS_DETECTION_POOL=4              # 主负载能力单独对齐核数
ARGUS_MAX_CONCURRENT_INFERENCE=10   # ≥ 各能力窗口数之和
ARGUS_SHUTDOWN_TIMEOUT_SECS=15      # 排队深度翻倍后重算
```

**C. GPU 单卡（以 A10 24G、只跑 detect 为例——先把一个能力算清楚）**

```bash
ARGUS_DEVICE=cuda
ARGUS_DETECTION_POOL=6              # 6 窗口 × ~3GB ≈ 18GB，24GB 卡留 ~6GB 余量
ARGUS_ENGINE_POOL=2                 # 其它能力各 2 窗口（若启用，按 §8.3 重算显存）
ARGUS_MAX_CONCURRENT_INFERENCE=12   # ≥ 6 + 其它各能力窗口数之和
ARGUS_GPU_MEM_LIMIT_MB=20000        # 进程级上限；< 物理显存，留 arena 之外的系统占用
# ARGUS_ACQUIRE_TIMEOUT_MS=0        # 生产防雪崩可选 fail-fast；内网低负载可留默认排队
```

> **场景 C 的算式说明**（避免两个池数混着看）：显存占用的正确算法是 **Σ(每个能力的窗口数) × ~3GB**，不是 `ENGINE_POOL` 与 `DETECTION_POOL` 相乘。上例若只启用 detection：6 × 3GB ≈ 18GB < 20GB 上限 < 24GB 物理显存，成立。**每增加一个能力就重算一次**，超了就压池或换更大显存的卡。

**D. GPU 多卡**：每卡一个实例（§5.5），env 同 C、端口不同；调度交给上层。

## 7. 常见误区 FAQ（普通使用者最容易踩的 8 个坑）

| # | 误解 | 事实 |
|---|---|---|
| 1 | "CPU 上把池开大，图片就处理得更快" | 核数守恒：总吞吐不变、单张更慢（§4.1）。共享机保持池 1 |
| 2 | "显存只占几个 G，买小显存的卡就行" | 那是单窗口；窗口数 × ~3GB 才是总量，arena 只增不减（§4.2） |
| 3 | "买了 GPU，图片就全在 GPU 上跑" | 解码/缩放/NMS 全在 CPU；GPU 机器同样要够多的 vCPU（§2.2、§5.4） |
| 4 | "大厅放行数越大越好" | 大厅 ≫ 窗口数只会让图片在队里干等，逼近排队超时 503；与窗口数对齐即可（§2.5） |
| 5 | "本地 A100 测试时 GPU 很闲，所以小卡就够" | 闲是因为当时每秒就几张图；每张图的 GPU 耗时固定，600 张/秒是另一种量级 |
| 6 | "600 张齐发，argus 会并行处理" | 默认池 1 时全在窗口栏杆前排队；队尾 ~24s 等待、逼近 30s 超时线（§2.6） |
| 7 | "直接上国产卡/ARM 服务器省成本" | 当前 argus 的 GPU 路径要 NVIDIA + x86（§5.4）；鲲鹏 CPU 版部署包另有一套（已验证可跑 CPU 推理） |
| 8 | "改 `ARGUS_ENGINE_POOL` 不用重启" | 池在启动时加载，改 env 需重启实例生效；动态槽（slots.toml）才支持热重载 |
| 9 | "CPU 核多，把 ORT 线程数从 4 调到 16，单张图就快 4 倍" | 【实测】ORT 1.26.0 sweep：4→16 只快约 10–20%（37.5→35.2ms 到顶），8 线程后平台期、16 抖动变大；固定核预算下"少线程多窗口"总吞吐反而更高（§3.1）。线程数目前写死在 fork 里，改它属于挂账项 §10.1 |

## 8. 从零配置一台机器（照着做）

### 8.1 第 1 步：先量单张图（10 分钟）

服务起来后，用一张真实业务图测独跑基线并存档：

```bash
curl -s -H "x-api-key: <token>" -F "file=@real.jpg" http://127.0.0.1:7042/detect
# 记录 data.inference_ms（本项目 2026-11-10 实测 83ms）；以后所有对比都以它为参照
```

### 8.2 第 2 步：按 §5.1 三个问题估 QPS，选场景

- 查 §5.2 决策树定 CPU/GPU 与机型；
- 从 §6 选 A/B/C/D 中最近的一档，把 env 写进 `argus.env`（部署布局约定见 README：路径用相对形式、`run.sh` 以自身目录为 cwd）。

### 8.3 第 3 步：改完必过的 5 项核对清单

1. `大厅放行数 ≥ Σ(各能力窗口数)`；
2. CPU：窗口数 × 4 ≤ 核数（共享机留邻居余量）；
3. GPU：Σ(各能力窗口数) × ~3GB ≤ `GPU_MEM_LIMIT` < 物理显存（留系统占用余量，§4.2 官方说明 arena 之外还有开销）；
4. `SHUTDOWN_TIMEOUT ≥ 最长推理 × 排队深度`；
5. 重启后验证：`/health` 的 `backpressure.max_concurrent` 等于大厅数；启动日志出现 `引擎 {capability} 池(N) 加载完成` 与逐实例预热日志；GPU 上 `nvidia-smi` 显存曲线稳定在上限内。

### 8.4 第 4 步：压测验证，再决定加不加资源

- 批量客户端并发数 ≈ `max_concurrent`（§2.6）；
- 观察 §9 的背压指标；
- **不达标先查瓶颈，再花钱**：queue_ms 大 → 放大门；inference_ms 被拉长 → 加窗口；GPU 利用率低而 CPU 满 → 加 vCPU 或做批处理（§10.2）；单张延迟不达标 → 参考 §4.5 的输入降档/换卡。

## 9. 诊断与观测（出问题先看这里）

- `/health` 的 `backpressure` 字段：`in_flight`（当前在办）/ `queued_total`（累计进过队）/ `rejected_total`（累计 503）/ `acquire_timeout_total`（累计排队超时）。`queued_total` 持续增长 = 门偏小或下游吞吐不足；`rejected / acquire_timeout` 增长 = fail-fast 或超时在触发。
- `queue_ms` 与 `inference_ms` 的判读见 §2.5；每次对比前先复测独跑基线（机器负载会变）。
- GPU 必看：`nvidia-smi` 显存曲线（arena 单调上涨属正常，撞 `GPU_MEM_LIMIT` 后异常）；首请求延迟是否被预热消除。
- 启动日志锚点：`引擎 {capability} 池(N) 加载完成`、`引擎池实例 i/N 预热完成`。

## 10. 未决项（挂账，均需改 fork/代码，当前不可用 env 解决）

1. **ORT 线程数 env 化**：改 fork `runtime_config.rs` 常量 + argus 透传；注意官方提醒手动设定后不再自动绑核（§3）。**验证方法**：先在独占机做 §3.1 那样的 sweep（固定模型/图/尺寸，正反序各一遍，同时记录 p50 与抖动），再按"延迟最优"与"吞吐最优"分别定值；不要把祖传 4 直接改成核数。
2. **服务端张量批处理**：`/detect/batch` 现为逐图 for 循环（`routes/batch.rs:4` 注明），真 batch 是 GPU 上突破单卡吞吐的下一杠杆（【估算】×2–4，需模型动态 batch 维度）。
3. **多 GPU 绑定**（单实例多 `device_id`）：需改 fork，当前用多实例替代（§5.5）。
4. **TensorRT EP 验证**：fork feature 现成、未实测，静态 shape 下【估算】×2–5。
5. **全局线程池 / 绑核**：官方提供的多 session 争抢治理手段【官方】，需评估是否引入 fork。
